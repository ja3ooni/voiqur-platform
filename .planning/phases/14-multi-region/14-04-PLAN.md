# Plan 14-04: DNS Geo-Routing + Cross-Region Sync + Phase Test Suite

**Phase:** 14 · multi-region
**Requirement:** MULTI-03 (+ integration coverage for MULTI-01..MULTI-04)
**Complexity:** High

## Objective

Complete the DNS geo-routing story (Route53 geolocation records with sovereignty-safe defaults), add the pull-based Prometheus federation pattern for control-plane metadata sync, expose a `/admin/v1/region/status` health endpoint that returns only aggregate non-PII fields, and ship the phase-level integration test suite that verifies all four MULTI requirements end to end.

## Tasks

### 1. ExternalDNS geo-routing — sovereignty-safe default record handling

The Frankfurt and UAE Ingress patches in Plans 14-01/14-02 already carry `aws-set-identifier` and `aws-geolocation-*` annotations. This task finalises the sovereignty-fallback semantics per RESEARCH open question 5.

**Decision (resolving RESEARCH open question 5):** No default catch-all record. Unmatched source IPs receive `NXDOMAIN`. Reasoning: silently routing unmatched traffic to either region would violate D-02/D-07. NXDOMAIN is the only response consistent with "reject rather than reroute".

- Edit `kiro/voiquyr/k8s/overlays/frankfurt/ingress-patch.yaml` to add:
  ```yaml
  external-dns.alpha.kubernetes.io/aws-geolocation-default-record: "false"
  ```
- Same change in `kiro/voiquyr/k8s/overlays/uae/ingress-patch.yaml`.
- Document the decision in `kiro/voiquyr/k8s/overlays/README.md` under a new "DNS sovereignty fallback" section.

### 3. Prometheus federation scrape config (control-plane metadata sync)

Create a new manifest `kiro/voiquyr/k8s/monitoring/prometheus-federation.yaml` (separate from any region overlay — this manifest is deployed in a neutral global control plane). Per RESEARCH §5:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: prometheus-federation-config
  namespace: voiquyr-global
data:
  prometheus.yml: |
    global:
      scrape_interval: 60s
      external_labels:
        role: federation
    scrape_configs:
      - job_name: 'frankfurt-federation'
        honor_labels: true
        metrics_path: '/federate'
        scheme: https
        tls_config:
          insecure_skip_verify: false
        params:
          'match[]':
            - '{job=~"voiquyr.*"}'
            - 'voiquyr_call_latency_ms_bucket'
            - 'voiquyr_flash_mode_hit_rate'
            - 'voiquyr_region_health_status'
        static_configs:
          - targets: ['prometheus.frankfurt.voiquyr.eu:9090']
            labels: { region: frankfurt, jurisdiction: eu }
      - job_name: 'uae-federation'
        honor_labels: true
        metrics_path: '/federate'
        scheme: https
        params:
          'match[]':
            - '{job=~"voiquyr.*"}'
            - 'voiquyr_call_latency_ms_bucket'
            - 'voiquyr_flash_mode_hit_rate'
            - 'voiquyr_region_health_status'
        static_configs:
          - targets: ['prometheus.uae.voiquyr.ae:9090']
            labels: { region: uae, jurisdiction: uae-pdpl }
```

Document in `kiro/voiquyr/k8s/monitoring/FEDERATION.md`:
- Pull-only (no push) — each region's Prometheus is authoritative.
- Whitelist of allowed metric names — anything not listed is dropped at the federate endpoint.
- mTLS required between global Prometheus and regional Prometheus.
- No PII allowed: ban regex `{__name__=~".*(audio|transcript|prompt|user_id|session_id).*"}` from scrape.

Add a Prometheus relabel-config rule (in the same ConfigMap) that drops any metric whose name matches the PII regex even if a regional Prometheus accidentally exposes it:

```yaml
    metric_relabel_configs:
      - source_labels: [__name__]
        regex: '.*(audio|transcript|prompt|user_id|session_id|customer).*'
        action: drop
```

**Test (TDD):**

  - Assert each `match[]` list is a whitelist (no `{__name__=~".*"}` patterns).
  - Assert the metric_relabel_configs contains a `drop` action with the PII regex.
- Expected: assertions pass.

## Notes

- D-02/D-07 sovereignty fallback: NXDOMAIN over silent reroute. The `aws-geolocation-default-record: "false"` annotation is the ExternalDNS knob that makes this real.
- Decision D-08/D-09: federation scrape config carries only aggregate metrics + the PII drop relabel rule. The drop rule is belt-and-suspenders — regional Prometheus instances also need a recording-rule allowlist (out of scope for this plan, may be a v1.2 hardening task).
- `RegionStatus` is intentionally minimal. Adding fields requires a privacy review — call this out in the docstring.
- The acceptance test marker creates a clear merge gate: `pytest -m acceptance` is the green-light for shipping Phase 14.
- Open question 6 from RESEARCH (External Secrets vs sealed-secrets) is not resolved here — both regions inherit whatever the base Helm chart uses today. Sealed-secrets vs ExternalSecrets choice is a v1.2 hardening task.
- Resolves RESEARCH open questions 3 (DNS zones: `voiquyr.eu` + `voiquyr.ae` confirmed) and 5 (sovereignty fallback: NXDOMAIN).
- If `pytest-acceptance` is not yet a registered marker, registering it avoids `PytestUnknownMarkWarning` failures under strict mode.
- The `RegionStatus` introspection test (asserting no PII field names) is the canonical guard against future contributors widening the schema. Keep it strict.
